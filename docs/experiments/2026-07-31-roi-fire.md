## Follow-up fire — F7 (Hermes pin)

**Problem:** cold Hermes install tracked floating `main`, so CI bit-rot / non-repro runs when upstream broke.

**Shipped:**
- `scripts/hermes-pin.sh` — resolve / install-args / matches / cache-suffix
- Default pin `53559aaf86b84dadae83cd9bb605ca476f9a0606` (NousResearch/hermes-agent main as of 2026-07-31)
- `run-hermes-review.sh` installs with `--skip-setup --commit <pin> --force-commit`; reinstalls on pin mismatch
- Workflow job env `TORII_HERMES_COMMIT` (override via repo var; `latest`/`main` = float)
- Cache key `torii-hermes-bin-${{ runner.os }}-v4-${{ pin_suffix }}`
- Trace copies `hermes-pin.txt`; tests in `tests/test_hermes_pin.py`

## Follow-up fire — F19 (re-trigger cooldown)

**Problem:** association allowlist stops strangers, but a teammate spamming `@torii review` still burns OpenRouter on every comment.

**Shipped:**
- `scripts/cooldown-check.sh` — fixture-testable; looks at latest successful `<!-- torii-review pr=N` comment age
- Default window 900s via `vars.TORII_COOLDOWN_SECONDS` (0/off disables)
- Failure stubs do **not** start cooldown (retry allowed)
- Bypass: `@torii review force`, `workflow_dispatch`, `TORII_COOLDOWN_FORCE=1`
- Workflow gates Hermes/checkout/post behind `steps.cooldown.outputs.allowed`; rocket reaction on skip
- Tests: `tests/test_cooldown_check.py`

## Follow-up fire — F10 (reusable workflow_call + thin caller)

**Problem:** multi-repo adoption meant copying a full pack; upgrading Torii required re-running install + PR on every target. F20 helped copy once but did not give free upgrades.

**Shipped:**

- Tests: `test_caller_mode_thin_only`, pack mode asserts reusable present

## Follow-up fire — F22 (verdict-aware done signal)

**Problem:** Done reaction was pipeline-only (`pipeline_rc=0` → 👍). A clean Hermes run that returned **REQUEST CHANGES** still looked like success on the trigger comment, and there was no commit status for branch protection.

**Shipped:**
- `scripts/parse-verdict.py` — normalize verdict aliases; map → reaction + commit-status state
- `scripts/report-verdict.sh` — soft reaction on trigger comment, soft `torii/review` status on PR head SHA, job-summary section
- Workflow step **Report verdict (F22)** replaces pipeline-only React result
- Mapping: APPROVE→+1/success · REQUEST CHANGES→-1/failure · COMMENT→eyes/success · pipeline fail→-1/error
- Opt-out: `vars.TORII_COMMIT_STATUS=0`; context override `vars.TORII_STATUS_CONTEXT`
- Install pack allowlist includes both scripts; tests: `tests/test_parse_verdict.py`

## Follow-up fire — F23 (formal GitHub PR Review event)

**Problem:** F22 put reaction + commit status on the trigger path, but the PR **Reviews** panel still had no Torii Gate review — operators only saw a long issue comment. REQUEST CHANGES did not show as a GitHub "Changes requested" review.

**Shipped:**
- `parse-verdict.py` emits `review_event=APPROVE|REQUEST_CHANGES|COMMENT` (pipeline fail → COMMENT)
- `report-verdict.sh` soft-posts `POST /pulls/{n}/reviews` with short body + marker `<!-- torii-pr-review pr=N`
- Full Markdown remains the F12 issue comment; dual channel is intentional
- APPROVE → soft-fallback to COMMENT when GitHub rejects (own PR / org policy)
- Opt-out: `vars.TORII_PR_REVIEW=0`
- Workflow wires `TORII_PR_REVIEW`; tests assert `review_event` mapping

## Follow-up fire — F24 (dismiss prior formal PR reviews)

**Problem:** F23 posts a Reviews-panel row each run, but re-triggers only replaced the issue comment (F12). Prior APPROVE/REQUEST_CHANGES rows stacked and confused merge UX.

**Shipped:**
- `scripts/dismiss-prior-pr-reviews.sh` — list reviews, match `<!-- torii-pr-review pr=N`, dismiss APPROVED/CHANGES_REQUESTED
- Wired from `report-verdict.sh` immediately before the new F23 submit
- Honours `TORII_REPLACE_PREVIOUS=0` (same as F12 comment replace)
- COMMENTED rows cannot be dismissed (GitHub API); logged as `skipped_commented`
- Fixture mode `TORII_PR_REVIEWS_FIXTURE` for hermetic tests; install pack allowlist updated
- Tests: `tests/test_dismiss_prior_pr_reviews.py`

## Follow-up fire — F25 (Hermes pin single source of truth)

**Problem:** `DEFAULT_HERMES_COMMIT` lived in `hermes-pin.sh` *and* as a workflow `env:` `|| '<sha>'` fallback. Bumping the pin required editing both or CI kept the stale SHA.

**Shipped:**
- `torii-review-reusable.yml` job env is pass-through `vars.TORII_HERMES_COMMIT` only
- New step **Resolve Hermes pin (F25)** after pack checkout: empty → `hermes-pin.sh default` → `$GITHUB_ENV`
- Cache-suffix step defensive fill from default if still empty
- `build-torii-runner.yml` same pass-through + existing resolve→default path + write `$GITHUB_ENV`
- Tests assert workflows no longer contain `|| '<DEFAULT_SHA>'`

## Follow-up fire — F27 (diff-truncation trust banner)

**Problem:** Large monorepo PRs hit `MAX_DIFF_BYTES` and still got a normal-looking Torii comment. The model was *asked* to note truncation under What I checked, but often didn't — operators couldn't tell reviews were incomplete.

**Shipped:**
- `normalize-review.py --diff-truncated` → ⚠️ banner before `**Verdict:**`
- `run-hermes-review.sh` reads `DIFF_TRUNCATED` from `meta.env` and passes the flag
- Job summary section when truncated
- Idempotent if banner already present; tests in `test_normalize_review.py`
